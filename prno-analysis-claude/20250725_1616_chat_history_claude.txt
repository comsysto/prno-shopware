> What is HMR development?

● HMR stands for Hot Module Replacement (also called Hot Module Reload). It's a development feature that allows you to see code changes instantly in your browser without having to
   manually refresh the page or lose your application state.

  How HMR Works

  When you make changes to your code during development:

  1. Traditional Development: You'd need to refresh the browser, losing any form data, navigation state, etc.
  2. With HMR: The development server detects file changes and automatically updates only the specific modules that changed, preserving your application state.

  In Shopware Context

  When you run:
  composer watch:admin        # Administration HMR server
  composer watch:storefront   # Storefront HMR server

  You get:
  - Instant Updates: Changes to Vue components, SCSS, or JavaScript appear immediately
  - State Preservation: Forms stay filled, modals remain open, navigation state persists
  - Faster Development: No manual refreshing or re-navigating to test changes

  Development URLs with HMR

  - Administration HMR: http://localhost:5773 - Vue 3 admin interface with instant updates
  - Storefront HMR: http://localhost:9998 - Customer interface with live reloading
  - Main Application: http://localhost:8000 - The actual Shopware instance

  Benefits for Shopware Development

  - Administration: Vue component changes update instantly while preserving complex form states
  - Storefront: CSS/SCSS changes apply immediately without losing shopping cart contents
  - Productivity: Significantly speeds up the development cycle, especially for UI work

  HMR is particularly valuable in Shopware because the administration interface is complex (lots of forms, modals, navigation states) and the storefront has intricate user flows
  (cart, checkout process) that would be tedious to manually recreate after each refresh.

  - Services and business capabilities
  - Runtime components that can be independently deployed
  - Logical units that external systems interact with

  - Code modules and namespace organization
  - Development artifacts (classes, interfaces, etc.)
  - Physical deployment units (though Shopware is monolithic)

  - Event handling is in /Framework/Event/ but used by all domains
  - DAL is in /Framework/DataAbstractionLayer/ but used everywhere
  - Rules are in /Framework/Rule/ but applied in Cart, Product, etc.

  4. Grouping Philosophy

  Repository Grouping (Domain-driven):
  - Groups classes that change together
  - Reflects business domain boundaries
  - Optimizes for team ownership

  C4 Grouping (Service-oriented):
  - Groups functionality by runtime responsibility
  - Shows service boundaries and API contracts
  - Reflects deployment and scaling units

● I've created a new C4 Component diagram that maps each component to its actual code location in the repository. Here are the key differences:

  New Diagram Features:

  1. Code Location Annotations

  Each component now includes its repository path:
  - Cart Service → /src/Core/Checkout/Cart/
  - Product Service → /src/Core/Content/Product/
  - Entity Repository → /src/Core/Framework/DataAbstractionLayer/EntityRepository.php

  2. Repository Structure Alignment

  Components are now organized by their actual domain folders:
  - Checkout Domain: Cart, Order, Payment, Customer, Shipping
  - Content Domain: Product, Category, CMS, Media, SEO, Rule
  - System Domain: Config, User, Language, Currency, Country, Tax
  - Framework Layer: DAL, Events, Rules, Plugins

  3. Physical Architecture Representation

  The diagram now reflects:
  - Folder-based grouping instead of purely logical grouping
  - Actual navigation paths developers use
  - Real code organization patterns

  4. Developer Navigation Guide

  Each component can be traced directly to source code:
  - Find component in diagram → Check location annotation → Navigate to repository path

  Key Benefits:

  1. Bridges Architecture-Code Gap: Links logical components to physical implementation
  2. Developer-Friendly: Easy to navigate from diagram to actual code
  3. Maintenance Support: Shows where to modify specific functionality
  4. Code Review Aid: Helps understand impact areas for changes

  Comparison with Previous Diagram:

  Previous (Logical): Focused on runtime behavior and service responsibilities
  New (Physical): Focuses on code organization and navigation

  Both diagrams serve different purposes:
  - Logical diagram: For understanding system architecture and component interactions
  - Physical diagram: For development, maintenance, and code navigation

  This new diagram makes it much easier for external development teams to understand not just what the components do, but where to find and modify the actual implementation.
